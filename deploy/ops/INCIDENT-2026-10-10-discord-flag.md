# 事件复盘 + 预案：Discord 应用被封（Application Growth Disabled / 680009）

**日期**：2026-10-10 ｜ **影响**：新用户无法领 Key（约 7.5 小时）｜ **严重度**：P1（核心入口中断，老用户不受影响）

## 一、发生了什么
Discord 信任与安全自动把应用（奶妹，App ID 1557999547261788291）判为 **Application Growth Disabled（错误码 680009）**：冻结一切新的 OAuth 授权（服务器安装 + 用户授权）。
因为**领 Key 的两条路（网页「用 Discord 登录」和 `/register`）都走 OAuth 授权**，所以新用户两条路全断。
- 最后一个成功注册：02:43（北京时间）；之后约 7.5 小时零新增。
- 老用户的 Key、出图：全程正常。

## 二、根因（三个都改了）
| # | 触发信号 | 整改 |
|---|---|---|
| 1 | 刚上线网页 Discord 登录 → 短时间 ~43 人授权一个**新应用**，且申请了敏感权限 `guilds.members.read` | OAuth 权限砍到只要 `identify`；`/register` 不再走 OAuth，改成从斜杠命令 interaction 直接发 Key |
| 2 | 机器人给每个新用户**私信**发 Key（批量私信是经典反滥用信号） | 不再私信；Key 只在本人可见的临时消息里给 |
| 3 | 画廊频道**自动点赞 ❤️ + AI 评论**（bot 自动互动内容，尤其涉及露骨图） | 全部关闭（`bot_gallery_like=0`、`bot_gallery_ai=0`）；bot 不再碰任何用户内容 |

## 三、修复（v2.9.0，已上线并验证）
- `/register` 直发 Key：interaction 已由 Discord 签名验明发起人，无需 OAuth。`service.issue_direct()` → 后端 `POST /self-register/issue` → 机器人临时消息回 Key。
- **效果**：不等 Discord 解封就恢复了领 Key（已有真实新用户领 Key + 出图成功验证）。
- 网页登录仍走 OAuth（已收到最小 `identify`），解封前用不了——但它只是查状态的便捷功能，非核心。
- 申诉已提交（唯一能彻底解封 + 恢复网页登录的途径）。

## 四、预案：平台/第三方依赖中断（通用）
**原则**：核心功能（领 Key、出图）绝不单点依赖任何可被第三方一键掐断的授权链路。

1. **身份验证优先用已鉴权的上下文，别无谓绕 OAuth**。斜杠命令 interaction、已签名的会话，本身就证明了身份——能不发起新授权就不发起。
2. **任何「自动化群发/群互动」默认关、可一键关**。私信、自动点赞、自动评论、@全体——都要有后台开关（`bot_gallery_*`、quiet 等），出事能 1 分钟内停。
3. **最小权限**。OAuth scope、Bot 权限、Intents 只要真正用到的；敏感 scope（guilds.members.read 等）能用 Bot Token 核验就别用用户授权。
4. **双通路**：面向用户的关键动作尽量有「不依赖该平台特性」的备用路（例：领 Key 既能网页也能 `/register` 直发）。
5. **监控已覆盖**：`nai-watch.sh` 盯「新注册、领取失败、拒绝、报错」；注册长时间零新增 = 预警信号。
6. **出事响应顺序**：① 先用后台开关停掉可疑自动化（止血）→ ② 查根因（日志 `admin_actions` 的失败记录、容器日志）→ ③ 上线绕开故障的修复（优先恢复核心）→ ④ 该平台的正式申诉 → ⑤ 发公告安抚用户。
7. **申诉要点模板**：小型非商业自用、成员自愿、已关闭所有自动化、已移除群发私信、权限收到最小、带 App ID + 错误码；一次性提交别重复。
