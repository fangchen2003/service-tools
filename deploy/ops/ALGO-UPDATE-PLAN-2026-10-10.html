1V4.5 成功率排查：结论是「信号误导」

奶妹提示「V4.5 成功率不高」。逐行查线上日志后：V4.5 本身是健康的，失败全部来自上游、且极少；体感「60 秒出不了图」是我们队列排队，不是上游变慢。

生成失败 = 上游，且很小

5 次失败集中在两个几分钟的窗口（02:39 两次 500、11:05 三次「上游流式生成失败」），不是持续问题，也不在我们最忙的时段。up_status=0 的本地失败 = 0。

「60 秒」= 我们的队列排队，不是上游慢

真正的生成耗时（dur_ms）V4.5 封顶 22s；「60s」来自排队（wait_ms p99 38s、max 63s）——单上游账号串行 + 晚高峰 + interval_jitter 节流的结果。这是我们在保护共享账号，不是上游故障。要降 V4.5 延迟，杠杆是网关容量设置（account_hourly_cap / key_image_queue / queue_per_account / 间隔），不是改上游。

奶妹为什么会误报（根因在代码）

指标本身是干净的——image_perf_rows 只取 status IN ('ok','error')，已排除「拒绝」（Vibe/img2img/额度/限流等本地闸）。误报来自 perf._flags 的 FAIL_FLOOR_1H：当某个低样本小时撞上一次上游 burst（如 11:05 的 3 次流式失败），那一小时成功率跌破 80% 就报「V4.5 最近 1 小时成功率 X%」，读起来像「V4.5 有问题」，实则是一次性上游抖动。又因库只有 ~17h、7 天基线为空，只有这条绝对阈值能触发。→ 见 §2 的 L11 修告警。

3Medium / 节约模式 已上线 v2.11.0

已交付（默认关，不改现状）

全站免费档可一键钳制到 14 步 + Euler-a（保留负面词），Anlas 约省 40%、出图更快。总览页「节约模式」按钮站长手动开关；autopilot 规则（默认 observe）在排队拥挤时可自动开、空闲时关。无论算法还是手动切换，都会在公告频道通知成员（带 1 小时防抖）。默认关闭、autopilot_economy 默认 observe，所以上线不改任何成员可见行为。

原理：NovelAI 的「节约模式」没有独立 API 字段——就是 14 步 + Euler Ancestral + 关 SMEA，省的 ~42% 全来自步数。我们 policy.py 的计价常量与官方一致，所以钳到 14 步就已按便宜 ~42% 扣费，V5 周额度按 (A+B·14)/(A+B·23) 自动少扣，不需要改上游。

要做的适配

  • 前端档位开关：免费档一键「节约 / 高质」；节约档锁 steps=14、sampler=k_euler_ancestral、关 sm/sm_dyn、不收自定义 UC。
  • 后端钳制：在 policy.clamp_image_params 加一条节约预设（已有 steps 钳制逻辑，扩展即可）。
  • 计费：无需改——现有公式按步数线性，V5 电池按 (A+B·14)/(A+B·23) 自动少扣。
  • 算法择机（autopilot 新规则，先 observe）：全站拥挤 / V5 池吃紧 / 排队 wait 偏高时，建议或默认把免费档切 Medium；空闲时放开 High。与现有「拥挤→调小份额」同源。

收益：同 Anlas 出图量 ×1.7，等价把人均额度提近一倍、或名额放宽更从容——是解「单号 Anlas 天花板」最便宜的杠杆，且与 L3 多号池叠加。

5本轮新增经验（penguinsama / minijiu / NAI 风控）

N5 · NAI 正在大力封号（最重要的背景）

社区情报：东亚/东南亚区转美元 + 信用卡购买被无条件拒绝；美国本土卡的账号也在 3 天内被无理由封禁清点；NAI 频繁扫用户 IP 属地，梯子换几个节点就封号；独享/共享号「绝迹」。minijiu 站出了 29 万图后「没号了」被迫暂停。

对我们的意义：我们这一个共享账号是极其珍贵且脆弱的资产。① 继续压低检测信号（间隔抖动、好公民限速、不群发）；② Discord 申诉务必推进；③ L3 多号池要重新评估——捐来的号本身也会被 NAI 封，多号池不等于安全，且接收他人账号在当前风控下风险更高。宁可慢、稳、少踩信号。

N1 · 「一个坏请求封掉账号」——我们已经安全

minijiu 踩过：有人发 2.5MB 超大请求 → NAI 返回 400 → 他们「按错误码自动处理」误把 3 个上游账号自动禁用了。我们核查过代码：只有 401 会自动停用账号；402/403 只提醒站长、明确不停用（注释写着「只有一把 Token 时自动停用会导致全站不可用」）；400 只透传、不停用。我们没有这个雷。
仍可补：入口加请求体积上限（N1，P2），把 2.5MB 这种超大请求在到上游/CF 之前就挡掉，避免 400 噪音和 CF 1015 连坐封站。

其余可借鉴（penguinsama 智绘姬站）

  • N2 图片输出格式可选（默认 WebP）：WebP 体积小、加载快，省用户和服务器流量；不兼容的客户端可在领 Key 页改「尊重请求」回退 PNG。我们也存图 + 返图，值得做（P2）。
  • N3 报错文案更清晰：他们的错误表很用户友好，例如「width 786 不是 64 的整数倍，最接近的合法值是 768」。我们已有不错的拒绝文案，可再补「最接近合法值」提示 + 一张公开的 HTTP 错误码对照表（P2）。
  • N4 「无限额度 + 全站排队」模型：penguinsama 不设每日次数、纯靠排队限流。是另一种取舍（体验上「不卡额度但要排队」）。我们单号 + 动态电池更适合保护稀缺算力，记为备选思路，不改。
  • N6 CF CDN 100s 硬约束再确认：必须 100s 内返回、不能发心跳（否则生图插件不兼容）。→ 节约模式（14 步）直接降低超时概率，和这条正相关。
