## 0. 总体结论

**没有 CRITICAL；不建议在修完下面 5 个“发布阻断项”之前开放注册。**

这个项目的安全基本功是扎实的：鉴权、功能开关、额度在所有生成路由上都到位，XSS 全部转义（线上用 `<img onerror>` 实测未触发），桥接接口对公网 404（大小写/双斜杠/%2F 变体均验证），上游 Token 从不进日志，3003/8000 端口公网不可达，槽位/预算在取消与异常时都能正确释放。

真正的风险集中在三类“**失败即放开**”的设计上：

1. **数值输入失败即“不限”**：空值/负数会变成 `0 = 不限`，包括全站 Anlas 预算——一次误操作就拆掉付费账号的保险丝。
2. **资源无上限的入口**：25 MB 的 JSON 体在事件循环里 `json.loads` + `deepcopy`，单个成员即可把 2 GB VPS 打到 OOM。
3. **共享锁跨网络 IO**：非流式文本请求、Discord 角色同步都在持锁时等外部服务，导致全站排队或计费记录丢失。

产品层面最大的问题是**规则太多且对成员不可见**（3 天不用就删 Key、15 秒间隔、免费档钳制、每日重置时点……），以及**后台手动建的 Key 默认“全部功能”**，与“新成员默认只开文生图”的设计相矛盾。

- 会话无法吊销：登出后旧 Cookie 7 天内仍有效（已复现）→ DB 中存 session 版本，登出递增。
- 登录限流：本地 XFF 可绕过；成功登录也计数会把站长自己锁 5 分钟；`FORWARDED_ALLOW_IPS=*` 让 compose 网内任意容器可伪造 XFF → 只计失败，信任 IP 改为 Caddy/网关 IP。

- NaN/Infinity、深层嵌套、`max_tokens:"abc"` → 500 而非 400（已复现，无信息泄露）。
- `/v1/me`、`/user/*` 无 RPM，每次鉴权都 `UPDATE+COMMIT`。

## 7. 部署 & 供应链

- **HIGH** `deploy/harden.sh`：`ufw --force reset` 后只放行 22，SSH 改过端口会把自己锁在外面；只检查 `/root/.ssh`；`systemctl reload ssh` 在 `sshd` 命名的发行版失败。
- `requirements.txt` 只有下限（可能解析到有 CVE 的 starlette/h11/python-multipart 旧版）→ `pip-compile --generate-hashes` 锁定 + `pip-audit`。
- 两个 Dockerfile 以 root 运行、无 HEALTHCHECK、基础镜像未锁 digest、无 `.dockerignore`；compose 建议 `cap_drop: [ALL]`、`no-new-privileges`、`mem_limit`、`read_only`。

## 8. 产品（PM 视角）

- **P0 上手断层**：成员领 Key 后没有任何“已连通”反馈，再叠加 3 天静默删除，慢热用户直接流失。→ `/v1/me` 返回“最近一次成功请求”；删除前私信提醒。
- **P1 限额概念过多**：张数/日、V5/日、全站 V5、Anlas 日/月/全站、RPM、每 Key 间隔、每 Token 间隔、429 冷却、免费钳制、模型范围、功能开关、每日清空、到期、闲置删除——站长和成员都难以预测行为。→ 做 2–3 个命名模板（体验/常规/信任），成员只看到模板名与“今日还能生成 N 张”。
- **P1 生命周期三套并存**（到期 + 每日清空 + 闲置删除）→ 选一个主机制。
- **P1 站长缺“今日一屏”**：被拒请求按原因分布、命中 429 次数、即将到期/删除的 Key、名额、预估 Anlas 泄漏。
- **P2 过度设计**：多 Token 池 + 每 Token V5 限额/并发 + Anlas 核对 + `/nai/ai/*` 别名，对 10 人规模增加了大量审查面 → 折叠到“高级”。
- 建议指标：周活 Key/已发 Key、注册→首次成功请求时长、按原因的拒绝率、排队 p50/p95、上游 429/天、被自动钳制的请求占比。

## 9. 架构建议

1. **每 Token 一个准入控制器**：按 Key 的 FIFO 队列轮询调度，图片与文本共用，限制每 Key 队列深度，并在**读 body 之前**准入 → 一并解决 B1、B4、幽灵请求、公平性。
2. **显式区分“排队中”与“已派发”两个阶段**：取消/断连检查只作用于排队阶段，超时与“计费不确定”只作用于派发阶段。
3. **统一的上游响应策略模块**：Retry-After 解析与钳制、401/429 分类、分道冷却，以及后台的“清除冷却 / 重新启用”。
4. **数据库写入收口到 `Database`**：禁止业务代码直接用 `db._db`，禁止持写事务 await 网络。
5. **输入校验收口**：模型名、数值字段在路由入口一次性规范化，用严格 schema（pydantic）替代散落的 `int()`。
6. **安全头与缓存策略做成中间件**，而不是逐路由添加。
